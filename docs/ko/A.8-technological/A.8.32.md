# A.8.32 변경 관리 (Change management)

| 구분 | 내용 |
|---|---|
| 표준 | ISO/IEC 27001:2022 Annex A |
| 테마 | A.8 기술적 통제 (Technological) |
| 통제 | A.8.32 변경 관리 |
| 통제 유형(참고) | 예방적 (Preventive) |
| 보안 속성(참고) | 기밀성 / 무결성 / 가용성 |
| ISMS-P 대응 | 2.9.1 변경관리 |
| 2013 대응 | A.12.1.2, A.14.2.2, A.14.2.3, A.14.2.4 |

## 통제 목적

정보처리시설 및 정보시스템(인프라, 애플리케이션, 구성, 절차)에 대한 변경을 통제된 절차에 따라 계획/검토/승인/시험/배포하여, 검증되지 않은 변경이 보안성이나 서비스 안정성을 훼손하는 것을 예방하기 위한 통제입니다. 변경의 영향과 위험을 사전에 평가하고, 권한 있는 자의 승인을 거쳐, 실패 시 원상복구가 가능한 상태에서 반영하도록 요구합니다. 이를 통해 변경으로 인한 장애/취약점 유입/무단 기능 변경을 줄이고, 변경 이력을 추적 가능하게 유지하는 것을 목표로 합니다.

## 주요 확인사항

1. 정보시스템/인프라/애플리케이션 변경에 대한 변경관리 절차가 문서화되어 있고, 적용 범위(정기/긴급/표준 변경 등)가 정의되어 있는가?
2. 변경 요청 시 목적, 영향 범위, 보안 영향, 위험, 롤백 방안이 사전에 검토되고 권한 있는 자의 승인을 받는가?
3. 변경 사항이 운영 반영 전에 시험 환경에서 검증되고 인수 기준을 충족하는지 확인되는가?
4. 긴급 변경에 대해 사후 검토/승인 및 기록을 포함한 별도 절차가 마련되어 운용되는가?
5. 변경 이력(요청/승인/시험/배포/결과)이 추적 가능한 형태로 기록/보존되며, 관련 문서(구성/운영 절차)가 함께 갱신되는가?
6. 변경 실패나 예기치 못한 영향 발생 시 원상복구(롤백)가 가능하도록 사전 준비 및 사후 확인이 이루어지는가?

## 이행 지침

- 변경 유형(표준/정기/긴급)별로 요청, 영향/위험 평가, 승인, 시험, 배포, 종료의 단계와 책임자를 정의한 변경관리 절차를 수립합니다.
- 변경 요청서에 변경 목적, 대상 자산, 보안/개인정보 영향, 상호 의존성, 예상 중단시간, 롤백 계획, 검증 방법을 포함하도록 표준화합니다.
- 변경자문(변경관리위원회 등) 또는 권한 있는 승인자가 위험 수준에 맞게 변경을 검토/승인하고, 요청자와 승인자를 분리하여 자기승인을 방지합니다.
- 변경은 운영과 분리된 시험 환경(A.8.31)에서 검증하고 인수 기준을 충족한 뒤, 운영환경 이관/배포 절차(A.8.19)에 따라 반영합니다.
- 배포 전 현재 구성/실행코드/데이터를 백업하고, 실패 시 정해진 시간 내 되돌릴 수 있는 롤백 절차를 사전에 준비/시험합니다.
- 긴급 변경은 신속히 처리하되 사후에 정식 검토/승인/기록을 완료하고, 모든 변경 이력과 구성/운영 문서, 보안 통제(방화벽 정책, 접근권한 등)를 변경에 맞춰 갱신합니다.

## 증적자료

- 변경관리 절차서 및 변경 유형(표준/정기/긴급) 정의 문서
- 변경 요청서/승인 기록(영향/위험 평가, 롤백 계획 포함)
- 변경 시험/인수 결과 및 운영 반영(배포) 기록
- 긴급 변경 처리 및 사후 검토/승인 기록
- 변경 전 백업 및 롤백 수행/검증 기록
- 변경자문(변경관리위원회) 회의록 또는 승인 이력, 변경에 따른 구성/운영 문서 갱신 내역

## 부적합 사례

- 변경관리 절차가 없거나 특정 시스템(예: 네트워크 장비, 클라우드 구성)에 적용되지 않아 통제 없이 변경이 반영되는 경우
- 영향/위험 평가나 승인 없이 운영 환경에 직접 변경을 반영하여 장애나 취약점을 유발한 경우
- 시험 환경 검증 없이 변경을 운영에 적용하거나, 요청자가 자기 변경을 스스로 승인하는 경우
- 긴급 변경을 처리한 뒤 사후 검토/승인/기록을 남기지 않아 변경 내역을 확인할 수 없는 경우
- 변경 전 백업이나 롤백 방안이 없어 변경 실패 시 서비스 복구가 지연된 경우
- 변경 이후 구성 문서, 접근권한, 보안 정책 등이 갱신되지 않아 실제 구성과 문서가 불일치하는 경우
