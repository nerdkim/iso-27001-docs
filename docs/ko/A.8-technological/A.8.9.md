# A.8.9 구성 관리 (Configuration management)

| 구분 | 내용 |
|---|---|
| 표준 | ISO/IEC 27001:2022 Annex A |
| 테마 | A.8 기술적 통제 (Technological) |
| 통제 | A.8.9 구성 관리 |
| 통제 유형(참고) | 예방적 (Preventive) |
| 보안 속성(참고) | 기밀성 / 무결성 / 가용성 |
| ISMS-P 대응 | 2.9.1 변경관리 |
| 2013 대응 | 2022 신규 |

## 통제 목적

구성 관리는 하드웨어, 소프트웨어, 서비스, 네트워크의 구성(보안 구성 포함)을 표준화된 기준선으로 정의/문서화하고, 이를 일관되게 적용/모니터링/검토하도록 요구하는 통제입니다. 승인되지 않은 구성 변경이나 시간이 지나면서 누적되는 구성 편차(drift)를 탐지하고 시정하여, 시스템이 의도한 보안 수준을 지속적으로 유지하도록 하는 것이 목적입니다. 안전하지 않은 기본값, 불필요한 기능, 일관성 없는 설정으로 인한 공격 표면 확대를 억제하는 데 기여합니다.

## 주요 확인사항

1. 자산 유형별(서버 OS, 네트워크 장비, DBMS, 미들웨어, 클라우드 서비스, 엔드포인트 등)로 보안 구성 기준선/템플릿을 정의하고 문서화하고 있는가?
2. 정의된 구성 기준선이 신규 도입/재설치/프로비저닝 시 실제로 적용되도록 배포 절차에 반영되어 있는가?
3. 운영 중 시스템의 실제 구성이 기준선과 일치하는지 주기적으로 점검하고, 편차(drift) 및 승인되지 않은 변경을 탐지하는가?
4. 구성 정보(설정값, 버전, 상호 의존관계, 담당자 등)를 최신 상태로 기록/관리하며 변경관리 절차와 연계되어 있는가?
5. 민감한 구성 정보(자격증명, 키, 상세 설정)에 대한 접근을 통제하고 안전하게 저장/전송하고 있는가?
6. 구성 기준선을 위협/취약점 변화에 맞춰 정기적으로 검토하고 갱신하는가?

## 이행 지침

- 자산 유형별로 보안 강화(하드닝) 요건을 반영한 구성 기준선/템플릿을 수립하고, 근거(벤더 권고, 산업 벤치마크, 내부 정책)를 함께 문서화합니다.
- 기본 계정/비밀번호 변경, 불필요한 서비스/포트/기능 비활성화, 로깅 및 시간 동기화 활성화 등 공통 하드닝 항목을 표준화합니다.
- 골든 이미지, 코드형 인프라(IaC), 구성관리 도구를 활용해 기준선을 자동으로 적용하여 수작업 오류와 편차를 줄입니다.
- 실제 구성과 기준선을 정기적/상시적으로 비교해 편차를 탐지하고, 승인되지 않은 변경은 원복하거나 변경관리 절차로 정식화합니다.
- 구성 항목(CI), 버전, 의존관계, 책임자를 CMDB/구성 저장소에 최신으로 유지하고 변경관리 및 자산관리와 연동합니다.
- 구성 파일 내 자격증명/키는 하드코딩을 피하고 비밀관리(vault), 접근통제, 암호화로 보호합니다.
- 위협 환경 및 신규 취약점 정보를 반영하여 기준선을 정기적으로 재검토/개정하고 개정 이력을 관리합니다.

## 관련 통제 및 속성

- ISO 27001 본문 연계: 7.5(문서화된 정보), 8.1(운영 계획 및 통제), 9.1(모니터링, 측정, 분석 및 평가)
- 인접 Annex A: A.8.32(변경 관리), A.8.19(운영 시스템에의 소프트웨어 설치), A.8.8(기술적 취약점 관리), A.5.9(정보 및 관련 자산의 목록), A.8.16(모니터링 활동)
- ISMS-P 대응: 2.9.1 변경관리 (보안 구성/하드닝 관점에서는 2.6.2 정보시스템 접근, 2.10.1 보안시스템 운영과도 연계)
- 2013 대응: 2022 신규 (ISO/IEC 27002:2022에서 신설된 통제)

## 증적자료

- 자산 유형별 보안 구성 기준선/하드닝 표준 문서
- 구성관리 도구/IaC 코드, 골든 이미지/템플릿 및 배포 기록
- 구성 편차 점검 결과 및 시정 조치 기록
- CMDB/구성 저장소의 구성 항목/버전/의존관계 기록
- 구성 변경 승인 및 변경관리 연계 기록
- 구성 기준선 정기 검토/개정 이력

## 부적합 사례

- 보안 구성 기준선이 정의되어 있지 않아 서버마다 설정이 제각각이고 하드닝 적용 여부를 확인할 수 없는 경우
- 기본 관리자 계정/비밀번호가 변경되지 않은 채 시스템이 운영되고 있는 경우
- 구성 편차를 점검하는 절차가 없어 승인되지 않은 설정 변경이 장기간 방치된 경우
- CMDB가 최신화되지 않아 실제 구성과 문서상 구성이 불일치하는 경우
- 구성 파일에 DB 접속 비밀번호/API 키가 평문으로 하드코딩되어 저장소에 노출된 경우
- 기준선을 최초 1회만 수립하고 이후 위협/취약점 변화에 맞춰 갱신하지 않은 경우
