# A.8.26 애플리케이션 보안 요구사항 (Application security requirements)

| 구분 | 내용 |
|---|---|
| 표준 | ISO/IEC 27001:2022 Annex A |
| 테마 | A.8 기술적 통제 (Technological) |
| 통제 | A.8.26 애플리케이션 보안 요구사항 |
| 통제 유형(참고) | 예방적 (Preventive) |
| 보안 속성(참고) | 기밀성 / 무결성 / 가용성 |
| ISMS-P 대응 | 2.8.1 보안 요구사항 정의 |
| 2013 대응 | A.14.1.2, A.14.1.3 |

## 통제 목적

애플리케이션을 개발하거나 도입/구매할 때 처리하는 정보의 민감도, 노출 환경, 접근/인증 특성, 거래 형태를 고려하여 보안 요구사항을 식별/명세/승인하고 이를 개발 및 도입 전 과정에 반영하기 위한 통제입니다. 보안 요구사항을 사후가 아니라 기획/설계 초기에 정의해야 취약점이 설계와 구현 단계에 내재되는 것을 예방하고 재작업 비용을 줄일 수 있습니다. 특히 공개망(인터넷)을 경유하는 애플리케이션 서비스와 전자거래는 전송/거래의 무결성, 부인방지, 미완결/오류/재전송 방지 등 추가 요구사항을 필요로 합니다.

## 주요 확인사항

1. 애플리케이션 개발/도입 시 처리 정보의 민감도와 노출 환경(내부망/공개망)에 따라 보안 요구사항을 식별/문서화하고 승인하는 절차가 있는가?
2. 인증/인가/세션 관리/접근통제에 대한 요구사항이 요구사항 정의서에 구체적으로 반영되어 있는가?
3. 입력 검증, 출력 인코딩, 안전한 오류 처리, 인젝션/변조 방지 등 애플리케이션 취약점 대응 요구사항이 정의되어 있는가?
4. 공개망을 경유하는 거래/전송에 대해 전송 암호화, 거래 무결성, 부인방지, 미완결/중복/재전송/오라우팅 방지 요구사항이 정의되어 있는가?
5. 개인정보/결제정보 등 법적/계약적 요구사항과 로깅/감사 추적 요구사항이 반영되어 있는가?
6. 정의된 보안 요구사항이 설계/구현/시험 단계에서 검증/시험되고 릴리스 전에 승인되는가?

## 이행 지침

- 애플리케이션 유형(웹/모바일/API/전자거래 등)과 처리 정보 등급, 노출 환경을 기준으로 보안 요구사항 카탈로그/체크리스트를 마련하고, 프로젝트 착수 단계에서 위험평가 결과에 따라 요구사항을 선정합니다.
- 인증(다중 인증 포함), 인가 및 권한 최소화, 세션 관리, 접근통제 요구사항을 명세하고, 신뢰수준이 다른 사용자/시스템 간 상호작용에 대한 통제 요구사항을 정의합니다.
- 입력 검증, 출력 인코딩/이스케이프, 안전한 오류 처리, 인젝션/XSS/CSRF/안전하지 않은 역직렬화 등 알려진 취약점에 대한 방어 요구사항을 안전한 코딩 표준(A.8.28)과 연계하여 정의합니다.
- 공개망/전자거래 애플리케이션에는 전송구간 암호화(TLS), 거래 무결성 및 부인방지(전자서명/타임스탬프), 메시지 미완결/중복/재전송/오라우팅 방지, 결제/정산 검증 요구사항을 정의합니다.
- 개인정보 및 결제정보를 처리하는 경우 관련 법규/기준(개인정보보호법, PCI DSS 등)과 데이터 보관/파기, 로깅/감사 추적 요구사항을 반영합니다.
- 정의한 보안 요구사항은 추적성(요구사항 ID)을 확보하여 설계/구현/시험(A.8.29)에서 검증하고, 도입(구매/SaaS) 제품의 경우 공급자의 보안 기능이 요구사항을 충족하는지 평가/승인합니다.

## 관련 통제 및 속성

- ISO 27001 본문 연계: 6.1(위험 및 기회 대응), 8.1(운영 계획 및 통제)
- 인접 Annex A: A.8.25(안전한 개발 생명주기), A.8.27(안전한 시스템 아키텍처 및 엔지니어링 원칙), A.8.28(안전한 코딩), A.8.29(개발 및 인수 시 보안시험), A.8.30(외주 개발), A.5.8(프로젝트관리 정보보안), A.8.24(암호 사용)
- ISMS-P 대응: 2.8.1 보안 요구사항 정의 (연계: 2.8.2 보안 요구사항 검토 및 시험, 2.6.3 응용프로그램 접근, 2.10.4 전자거래 및 핀테크 보안)
- 2013 대응: A.14.1.2(공개 네트워크 응용서비스 보안), A.14.1.3(응용서비스 거래 보호)

## 증적자료

- 애플리케이션 보안 요구사항 정의서/체크리스트 및 승인 기록
- 요구사항 도출 근거가 되는 위험평가 및 데이터 등급 분류 결과
- 인증/인가/접근통제/세션 관리 설계 문서
- 공개망/전자거래 요구사항(전송 암호화, 거래 무결성, 부인방지 등) 명세 및 적용 내역
- 보안 요구사항에 대한 시험/검증 결과(설계 검토, 보안 시험 보고서)
- 도입 애플리케이션의 공급자 보안 요구사항 충족 평가 및 승인 문서

## 부적합 사례

- 애플리케이션 개발/도입 시 보안 요구사항을 별도로 정의하지 않고 기능 요구사항만으로 진행한 경우
- 공개망을 경유하는 거래에 전송 암호화/거래 무결성/부인방지 요구사항이 정의되지 않은 경우
- 입력 검증/인젝션 방지 등 취약점 대응 요구사항이 없어 동일 유형의 취약점이 반복 발생하는 경우
- 개인정보/결제정보 처리에 대한 법적 요구사항이 보안 요구사항에 반영되지 않은 경우
- 정의된 보안 요구사항이 시험/검증 단계에서 확인되지 않은 채 릴리스된 경우
- 도입(구매/SaaS) 애플리케이션의 보안 기능이 요구사항 충족 여부를 평가받지 않고 도입된 경우
